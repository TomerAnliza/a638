## המתודולוגיה: SDD — Spec-Driven Development

**המפרט קודם לקוד.** זה הכלל שקובע הכול.

### מבנה מפרט

כל יכולת (feature) חיה בתיקייה משלה תחת `specs/`:

```text
specs/
└── NN-feature-name/
    ├── spec.md     # מה ולמה — דרישות, קריטריוני קבלה, מה מחוץ לתחום
    ├── plan.md     # איך — ארכיטקטורה, קבצים שישתנו, החלטות וחלופות שנדחו
    └── tasks.md    # רשימת משימות ממוספרות, כל אחת עם תוצר ברור וסטטוס
```

### מחזור החיים של יכולת

| שלב | תוצר | מי מאשר |
|---|---|---|
| 1. מפרט | `spec.md` עם סטטוס `draft` | בעל הפרויקט מעלה ל-`approved` |
| 2. תכנון | `plan.md` | בעל הפרויקט |
| 3. פירוק | `tasks.md` — כל משימה קטנה מספיק לסשן אחד | סוכן מתכנן |
| 4. מימוש | קוד + בדיקות, משימה אחת בכל פעם | בדיקות עוברות |
| 5. אימות | `spec.md` עובר ל-`done`, יומן מעודכן | בעל הפרויקט |

### סטטוסים

`draft` → `approved` → `in-progress` → `done`
וגם `blocked` (עם סיבה) ו-`rejected` (עם סיבה).

### כללי SDD שאינם ניתנים למיקוח

1. **אין קוד בלי מפרט מאושר.** נתבקשת לכתוב קוד ואין מפרט? כתוב מפרט קודם, ובקש אישור
2. **שינוי דרישה מתחיל ב-`spec.md`**, לא בקוד
3. **סתירה בין קוד למפרט** — עוצרים, מדווחים, מתקנים במפורש את אחד מהם
4. **קריטריון קבלה חייב להיות ניתן לבדיקה.** לא "עובד טוב" אלא "מחזיר 200 עם JSON תקין"
5. **משימה שהושלמה מסומנת ב-`tasks.md`** באותו סשן, לא "אחר כך"

## תפקידי הסוכנים

[להתאים לפרויקט. התבנית שלהלן היא נקודת פתיחה.]

| תפקיד | אחראי על | אינו נוגע ב |
|---|---|---|
| **מתכנן** (planner) | `spec.md`, `plan.md`, `tasks.md` | `src/`, `tests/` |
| **מממש** (implementer) | `src/`, משימה אחת מ-`tasks.md` בכל פעם | מפרטים — מדווח, לא משנה |
| **בודק** (tester) | `tests/`, הרצת בדיקות, דיווח כשלים | `src/` — מדווח, לא מתקן |
| **סוקר** (reviewer) | ביקורת קוד מול המפרט, אבטחה, איכות | לא כותב קוד — רק מדווח |
| **מתעד** (scribe) | `docs/journal/`, `README.md`, סטטוסים | קוד ומפרטים |

**הכלל שמאחורי הטבלה:** התחומים **אינם חופפים**. שני סוכנים לא עורכים אותו
קובץ במקביל. סוכן שנדרש לשנות משהו מחוץ לתחומו — **מדווח, לא מבצע.**

## התחלת סשן

```text
1. קרא AGENTS.md (קובץ זה)
2. קרא את המפרט הפעיל (specs/ — סטטוס in-progress)
3. בדוק את רשומת היומן האחרונה ב-docs/journal/ — מה קרה בסשן הקודם
4. רק אז — התחל
```

## סדר עבודה בכל סשן

1. **בחר משימה אחת** — מ-`tasks.md`, בסטטוס פתוח, ושייכת לתחום שלך
2. **סמן אותה `in-progress`** לפני שמתחילים, כדי שסוכן אחר לא ייקח אותה
3. **בצע** — בתוך התחום שלך בלבד
4. **אמת** — הרץ בדיקות. כשל? דווח עם הפלט המלא, אל תסתיר
5. **סמן `done`** ב-`tasks.md`, וכתוב רשומה ב-`docs/journal/`
6. **דווח** — לפי פורמט הדיווח שלהלן

## סוכני-משנה (subagents)

כשסוכן מפעיל סוכן-משנה:

- תן לו את **המשימה המדויקת** מ-`tasks.md` ואת נתיב המפרט — לא תיאור חופשי
- הגדר במפורש **אילו קבצים הוא רשאי לערוך**
- סוכן-משנה אינו מסמן משימה כ-`done` — הסוכן הראשי מאמת ומסמן
- סוכן-משנה כפוף לאותם גבולות שבקובץ זה

## דיווח בסוף משימה

כל תשובה מסכמת עונה על ארבע שאלות, בסדר הזה:

1. **מה נעשה** — ברמת הקבצים והמשימות, לא ברמת הכוונות
2. **מה אומת** — אילו בדיקות רצו ומה הפלט. כשל מדווח עם הפלט המלא
3. **מה לא נעשה** — ולמה
4. **מה הלאה** — המשימה הבאה הפתוחה ב-`tasks.md`

## גבולות — מה אסור

- **אין פעולות הרסניות ללא אישור מפורש:** מחיקת קבצים, `git push --force`, `rm -rf`,
  שינוי סכמת בסיס נתונים, שינוי בהגדרות ייצור
- **אין קומיט ואין push** אלא אם נתבקשת במפורש באותה הודעה
- **אין סודות בקוד.** מפתחות API במשתני סביבה בלבד, לעולם לא בקובץ ולא בפלט
- **אין פעולה כלפי חוץ ללא אישור:** שליחת הודעה, פרסום, תשלום, קריאה ל-API שמשנה מצב
- **אין "תיקון תוך כדי"** מחוץ למשימה שנבחרה. ראית באג אחר? פתח משימה, אל תתקן
- **אין הנחות שקטות.** אי-ודאות שמשנה את התוצאה — שאל או ציין במפורש בדיווח

## תיעוד

- כל פעולה משמעותית מתועדת ב-`docs/journal/YYYY-MM-DD-topic.md` **לפני** סיום המשימה
- **תאריכים מוחלטים תמיד** — "20 באוקטובר 2026", לא "היום"
- **אין מחיקת תיעוד.** רשומה שגויה מתוקנת ברשומה חדשה שמפנה אליה
- רשומת יומן עונה על: מה נעשה, **למה** כך ולא אחרת, מה אומת, מה נשאר פתוח

- כל טקסט למשתמש, כולל עדכוני ביניים — **עברית**
